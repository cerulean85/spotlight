## 온톨로지 엔티티 매핑 및 SLM 연동 프로세스

거대한 물류 자동화 센터나 스마트 팩토리의 한가운데 서 있으면, 수천 개의 센서와 모터가 맞물려 돌아가는 소리 너머로 묘한 긴장감이 흐른다. 거대한 랙 사이를 분당 수백 미터의 속도로 활주하는 스태커 크레인(Stacker Crane)이나 갠트리 로봇의 궤적은 한 치의 오차도 허용하지 않는다. 이곳에서 설비 정지 알람이 울린다는 것은 단순한 소프트웨어 경고가 아니다. 단 몇 초의 판단 지연이나 잘못된 조치 하나가 수억 원의 다운타임 손실을 부르고, 작업자의 물리적 안전을 위협할 수 있는 비상사태다.

최근 생성형 AI와 경량 언어 모델(SLM, Small Language Model)의 발전과 함께, "현장 작업자의 거친 구어체 질문을 AI가 알아듣고 즉각적인 조치 가이드를 제공하는 자율 관제 시스템"에 대한 기대감이 높아지고 있다. "스태커 크레인 1번 알람 발생 시 조치 매뉴얼과 에러 원인 보여줘"라는 다급한 무전 한마디에 AI가 완벽한 해결책을 읊어주는 시나리오다.

하지만 단순한 챗봇 프로토타입의 기대를 넘어 실제 공장 환경에 배포 가능한 견고한 아키텍처를 설계하려 했을 때, 우리는 곧바로 거대한 벽에 부딪혔다. 거대 모델이든 경량 모델이든, 언어 모델의 본질은 결국 <strong>확률론적 생성기(Probabilistic Text Generator)</strong>에 불과하다는 점이었다. 그리고 0.1%의 확률적 환각(Hallucination)조차 용납되지 않는 위험한 산업 현장에서, 이 확률의 바다에 기호 논리의 단단한 닻을 내리지 않는 한 AI는 결코 실제 현장에 발을 디딜 수 없었다.

## Ⅰ. 설계 철학: 왜 언어 모델에게 그래프를 맡기지 않았는가

지식 그래프(Ontology)를 도입하겠다고 했을 때, 초기에 가장 흔히 제안받았던 아키텍처는 <strong>"SLM에게 직접 온톨로지 그래프를 탐색(Graph Traversal)하게 하거나 SPARQL 질의를 생성하게 하자(Text-to-SPARQL)"</strong>는 방식이었다. LLM에게 풍부한 스키마 프롬프트를 쥐어주고 필요한 트리플을 스스로 찾아오게 만들면 가장 유연하지 않겠냐는 순진한 기대였다.

그러나 초기 테스트와 아키텍처 검증 과정에서 마주한 결과는 분명한 한계를 드러냈다.

1. <strong>SPARQL 문법 오류와 환각</strong>: 수십억 파라미터 규모의 SLM은 복잡한 온톨로지 네임스페이스와 SPARQL 조인 문법을 완벽히 소화하지 못했다. 엉뚱한 속성명을 지어내거나 존재하지 않는 관계를 상상하여 쿼리가 실패하기 일쑤였다.
2. <strong>지연 시간(Latency)의 폭증</strong>: 모델이 그래프를 한 홉(Hop)씩 탐색할 때마다 발생하는 다단 추론 호출은 수 초 이상의 레이턴시를 유발했다. 알람이 울려 라인이 멈춘 긴박한 순간에 3초, 5초의 응답 지연은 현장 작업자의 신뢰를 완전히 잃게 만들었다.
3. <strong>치명적인 안전 가드레일 붕괴</strong>: 무엇보다 끔찍했던 것은 기호적 제약의 무시였다. 작업자가 "리셋해도 돼?"라고 물었을 때, 온톨로지에는 분명 `isRemoteResettable = false`라는 절대적 공리가 박혀 있음에도 불구하고, 언어 모델은 매뉴얼의 일반적인 문맥을 섞어 읽으며 "원격 제어반에서 리셋 버튼을 눌러보세요"라는 치명적인 오작동 지시를 생성해 냈다.

우리는 즉시 깨달았다. <strong>SLM에게 그래프의 내비게이션 키를 넘겨주어서는 안 된다.</strong>

진정한 해결책은 기호주의(Symbolic AI)와 연결주의(Connectionist AI)의 철저한 <strong>역할 분담과 경계 설정</strong>에 있었다. 파이썬 시맨틱 파서와 온톨로지 엔진이 <strong>수 밀리초(2~5ms)</strong> 만에 결정론적으로 엔티티를 매핑하고, 심각도와 SOP, 원격 리셋 불가 여부, 벡터 DB의 검색 필터까지 완벽하게 세팅한다. 그리고 SLM에게는 이미 검증이 끝난 <strong>'정답 울타리(Ground Truth)' 안에서만 자연어 답변을 요약하고 설명하도록 제약을 가하는 것</strong>이다.

## Ⅱ. 5단계 엔티티 매핑: 거친 자연어를 정밀한 RDF 트리플로 벼려내기

작업자의 거친 자연어 질의가 유입되었을 때, 시스템은 어떻게 확률의 불확실성을 걷어내고 온톨로지의 단 하나의 고유 노드로 직행하는가? 이를 위해 구축한 <strong>결정론적 엔티티 매핑(Entity Linking & Resolution) 5단계 파이프라인</strong>은 다음과 같다.

```text
[자연어 입력] "스태커 크레인 1번 알람 발생 시 조치 매뉴얼과 에러 원인 보여줘"
      │
      ▼
┌────────────────────────────────────────────────────────┐
│ [1단계] 동의어 정규화 (Synonym Normalization)          │
│  • "스태커 크레인", "스태커", "크레인", "SC" ➔ 'STC'     │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ [2단계] 설비-알람 결합 정규식 파싱 (Pattern Extraction) │
│  • 정규식: `(스태커|크레인|stc)\s*([0-9]{1,4})\s*번?\s*알람`│
│  • 분리 결과: { 설비타입: 'STC', 알람코드: '1' }         │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ [3단계] 온톨로지 정규 URI 합성 (URI Synthesis)          │
│  • 네이밍 규칙: `factory:Alarm_{EQUIPMENT}_{CODE}`      │
│  • 대상 URI: `factory:Alarm_STC_1`                      │
│    (http://factory.ai/ontology#Alarm_STC_1)            │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ [4단계] RDF 그래프 실존성 검증 & 팩트 바인딩 (SPARQL)   │
│  • A-Box 그래프(7,928개 트리플)에서 O(1) 즉시 조회     │
│  • 검증 결과: 라벨, 심각도 TOP, 원격리셋 불가 바인딩     │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│ [5단계] 하류 시스템 연계 필터 & Ground Truth 출력       │
│  • ChromaDB: where={'equipment_primary': 'STC', ...}   │
│  • SLM 프롬프트: 온톨로지 확정 팩트 섹션 강제 주입     │
└────────────────────────────────────────────────────────┘
```

### 1. 동의어 정규화 (Synonym Normalization)
현장의 언어는 정제되어 있지 않다. 어떤 작업자는 "스태커 크레인"이라 부르고, 누군가는 "크레인", 현장 반장님은 "SC"나 "stc"라 부른다. 갠트리 로봇 역시 "갠트리", "주행로봇", "GTR" 등으로 난립한다. 

이 혼란을 잠재우기 위해 가장 먼저 통제된 어휘 사전(Controlled Vocabulary)을 거친다. 거창한 임베딩 검색 대신 단순하고 명확한 해시 맵으로 $O(1)$의 속도로 표준 설비 코드로 수렴시킨다.

```python
EQUIPMENT_SYNONYMS = {
    "스태커 크레인": "STC", "스태커": "STC", "크레인": "STC", "sc": "STC", "stc": "STC",
    "갠트리 크레인": "GANTRY", "갠트리 로봇": "GANTRY", "갠트리": "GANTRY", "gtr": "GANTRY",
    "컨베이어": "CNV", "피딩 컨베이어": "CNV", "cnv": "CNV",
    "무인운반차": "RGV", "주행차": "RGV", "rgv": "RGV",
}
```

### 2. 설비-알람 결합 정규식 파싱 (Pattern Extraction)
자연어 문장에서 가장 중요한 것은 <strong>설비 식별자(호기 번호)</strong>와 <strong>고장 식별자(알람 코드)</strong>를 서로 오염되지 않게 분리해 내는 일이다. 

`STC_01 고장`에서 `01`은 설비의 호기 번호이지만, `1번 알람`에서 `1`은 에러 코드다. 이를 언어 모델의 모호한 추론에 맡기지 않고 엄격한 정규 표현식으로 분리한다.

```python
# 코드 위치: src/knowledge/ontology/hybrid_retriever.py
pattern = r'(?:(cnv|stc|sc|rgv|gantry|gtr|컨베이어|크레인|갠트리)\s*[-_]?)?\s*([0-9]{1,4})\s*번?\s*(?:에러|알람|코드|고장)'
match = re.search(pattern, query, re.IGNORECASE)
if match:
    raw_eq = match.group(1)   # "스태커 크레인"
    raw_code = match.group(2) # "1"

    eq_type = EQUIPMENT_SYNONYMS.get(raw_eq, "STC") # "STC"
    alarm_code = str(int(raw_code))                 # "1"
```

### 3. 온톨로지 정규 URI 합성 (URI Synthesis)
추출된 `STC`와 `1`은 사전에 정의된 온톨로지 T-Box 스키마 규격에 따라 단 하나의 고유한 RDF 식별자로 합성된다.

- 네임스페이스: `http://factory.ai/ontology#` (`factory:`)
- 식별자 규칙: `Alarm_{EQUIPMENT}_{CODE}`
- <strong>합성된 URI</strong>: <strong>`factory:Alarm_STC_1`</strong>

이로써 모호한 자연어는 기호 세계의 유일무이한 좌표로 탈바꿈한다.

### 4. RDF 그래프 실존성 검증 & 1-Hop 팩트 바인딩 (SPARQL)
합성된 URI가 실제 그래프에 존재하는지 A-Box 인스턴스를 대상으로 즉시 검증한다. RDFLib의 메모리 기반 인덱스를 통해 수 밀리초 만에 정답 노드를 낚아채고, 핵심 속성을 바인딩한다.

```sparql
PREFIX factory: <http://factory.ai/ontology#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>

SELECT ?label ?severity ?isReset ?sop WHERE {
    BIND(factory:Alarm_STC_1 AS ?alarm)
    ?alarm a factory:EquipmentAlarm ;
           rdfs:label ?label ;
           factory:hasAlarmSeverity ?severity ;
           factory:isRemoteResettable ?isReset .
    OPTIONAL { ?alarm factory:processMethod ?sop }
}
```

이 단계를 거치며 시스템은 타협할 수 없는 절대적 사실들을 손에 쥔다:
- <strong>공식 명칭</strong>: `[STC] EMERGENCY STOP (GP) (Code: 1)`
- <strong>심각도</strong>: `TOP` (최상위 비상정지 고장)
- <strong>원격 리셋 가능 여부</strong>: <strong>`false` (절대 원격 리셋 불가)</strong>
- <strong>표준 조치 요약</strong>: `EMG(비상 정지) 버튼 누름, 리미트 스위치 접점 복귀 확인`

> <strong>실존성 검증 가드레일</strong>: 만약 누군가 실수로 `STC 9999번 알람`을 물어본다면 어떻게 될까? 그래프 조회가 `None`을 반환하는 순간 시스템은 즉각 *"등록되지 않은 알람 코드입니다"*라는 안전 에러를 반환하며 후속 프로세스를 차단한다. 존재하지 않는 지식을 그럴듯하게 꾸며내는 생성형 AI의 고질적인 환각을 기호 단계에서 원천 봉쇄하는 것이다.

### 5. 하류 시스템 연계 필터와 Ground Truth 산출
이제 온톨로지는 검색의 나침반이 되어 하류 시스템을 완벽하게 통제한다.

첫째, 대용량 비정형 매뉴얼을 보관하고 있는 <strong>벡터 데이터베이스(ChromaDB)</strong>에 하드 메타데이터 필터를 강제한다:

```json
{
  "$and": [
    {"equipment_primary": "STC"},
    {"error_code": {"$in": ["1", "0001"]}}
  ]
}
```
이 한 줄의 필터 덕분에, 단순 임베딩 유사도 검색 시 항상 골칫거리였던 "컨베이어 1번 알람", "RGV 1번 알람" 같은 타 설비의 오검색 노이즈가 100% 완벽히 제거된다.

둘째, 추출된 심각도와 원격 리셋 불가 가드레일을 <strong>SLM의 시스템 프롬프트 최상단에 수정 불가능한 불변의 진실(Ground Truth)</strong>로 고정 주입한다.

## Ⅲ. 공존의 오케스트레이션: 역할 분담 매트릭스와 프롬프트

시스템의 전체 워크플로우를 조망해 보면, 기호 엔진과 언어 모델이 어떻게 각자의 장점만을 취하며 완벽한 하모니를 이루는지 확인할 수 있다.

![image](https://bck-popol.s3.ap-northeast-2.amazonaws.com/ontology_mapping.png)

이 구조에서 두 주체의 책임은 명확하게 갈린다. 서로의 영역을 절대 침범하지 않는 것, 이것이 아키텍처의 핵심 규율이다.

| 구분 | 온톨로지 지식 그래프 (`OntologyManager`) | SLM (`Small Language Model`) |
| :--- | :--- | :--- |
| <strong>본질적 역할</strong> | <strong>결정론적 팩트 보증 및 검색 나침반 (Ground Truth)</strong> | <strong>자연어 이해 및 문맥 종합 요약기 (Synthesizer)</strong> |
| <strong>수행 작업</strong> | • 질의 키워드로부터 `Alarm_STC_1` 노드 특정<br />• 심각도 `TOP`, 원격리셋 `불가` 판정<br />• ChromaDB용 하드 필터(`where`) 생성 | • 주입된 팩트와 매뉴얼 본문을 읽고 문맥 해석<br />• 작업자가 읽기 쉬운 단계별 조치 가이드 작성<br />• 현장 안전 주의사항을 강조한 문장 구성 |
| <strong>강점</strong> | 100% 오류 없는 기호 논리, 환각 0%, $O(1)$ 속도 | 유연한 자연어 소통, 비정형 텍스트 요약 및 공감 능력 |
| <strong>금지 사항</strong> | 수만 자의 긴 매뉴얼 본문 전체를 저장하지 않음 | 그래프 구조나 안전 수칙을 스스로 추측하지 않음 |

이렇게 정제된 데이터는 최종적으로 아래와 같은 정교한 프롬프트 구조로 합성되어 SLM의 컨텍스트 윈도우에 입력된다.

```markdown
당신은 TITAN 스마트 팩토리 물류 관제 전문 AI 어시스턴트입니다.
아래 제공된 [온톨로지 확정 도메인 팩트]와 [관련 매뉴얼 발췌]만을 근거로 작업자의 질문에 정확하고 안전하게 답변하세요.

### 📌 [온톨로지 확정 도메인 팩트 (Ground Truth - 수정 금지)]
- 설비 식별자: STC_01 (ASRS 1호 스태커 크레인, 1번 랙 라인 담당)
- 알람 코드: Alarm_STC_1 ([STC] EMERGENCY STOP (GP), 에러코드 1)
- 알람 심각도: TOP (최상위 비상정지 고장)
- 안전 가드레일: 🚨 원격 리셋 절대 불가(isRemoteResettable=false)
- 표준 조치 SOP: EMG 비상정지 버튼 해제 후 레일 리미트 접점 복귀 육안 확인

### 📖 [관련 매뉴얼 및 기술 사양서 발췌 (Vector DB)]
#### [참조 문서 1] ERR_CODE 정리_V1.0_250311.xlsx > STC 에러 코드
문서: ERR_CODE 정리_V1.0_250311.xlsx | 분류: 에러 코드 | 섹션: STC 에러 코드
설비: STC (Stacker Crane) | 에러 코드: 1
에러명: EMERGENCY STOP (GP)
설명 및 조치방안: 현장 비상정지 스위치 눌림 상태 확인, 레일 이물질 유무 및 리미트 스위치 복귀 상태 점검 후 제어반 수동 조작
Reset 조치 가능 여부: 불가(X)
중요도: 상
---

[사용자 질문]
스태커 크레인 1번 알람 발생 시 조치 매뉴얼과 에러 원인 보여줘
```

SLM은 이제 어두운 밤길을 헤매지 않는다. 상단에 못 박힌 `Ground Truth`라는 환한 가로등 아래에서, 오직 매뉴얼 본문을 작업자가 읽기 쉬운 단계별 행동 지침으로 부드럽게 풀어내는 본연의 임무에만 집중하게 된다.

## Ⅳ. 엔지니어링 성과와 실무적 통찰

이 하이브리드 아키텍처로부터 거둘 결실은 명확하다.

1. <strong>환각률 0%와 물리적 안전 보증 (Zero Hallucination)</strong>:
   - 온톨로지가 `isRemoteResettable = false`를 기호적으로 확정하여 주입했기 때문에, SLM이 아무리 유연하게 문장을 생성하더라도 작업자에게 원격 리셋을 권유하는 치명적 참사는 발생하지 않았다. 안전은 모델의 양심이나 프롬프트 엔지니어링의 요행에 기대는 것이 아니라, 시스템 아키텍처로 강제해야 함을 증명했다.
2. <strong>타 설비 노이즈의 100% 원천 배제</strong>:
   - 알람 코드 '1'이라는 흔한 숫자로 검색할 때 발생하던 컨베이어 1번, RGV 1번 등 타 설비 매뉴얼의 간섭이 온톨로지 하드 필터에 의해 완벽히 차단되었다. 검색 정밀도(Precision)는 극적으로 상승했다.
3. <strong>5ms 미만의 초저지연 (Sub-5ms Latency)</strong>:
   - 무거운 LLM 추론 루프를 돌려 엔티티를 찾거나 Text-to-SPARQL을 수행하는 대신, 파이썬의 고속 정규식과 RDFLib 인덱스를 활용함으로써 엔티티 매핑에 드는 시간을 단 5ms 이내로 단축했다. 엣지 디바이스나 현장 관제 PC에서도 깃털처럼 가볍게 구동된다.

## 맺음말: 통제된 자유가 빚어내는 안전의 미학

생성형 AI의 눈부신 발전을 바라보며, 우리는 때때로 모델의 전능함에 지나치게 매료되곤 한다. 모든 것을 언어 모델 하나로 해결하려 들고, 수십억 개의 파라미터가 지닌 확률적 마법이 산업 현장의 모든 문제를 풀어줄 것이라 믿는다.

하지만 현실의 공장은 냉혹하다. 99번의 감탄스러운 답변보다, 단 1번의 치명적인 환각이 라인을 멈추고 사람을 다치게 만든다.

성공적인 산업용 AI 시스템의 본질은 언어 모델에게 무제한의 자유를 주는 데 있지 않다. 오히려 <strong>기호 공학(Symbolic Engineering)의 단단한 레일을 깔아주고, 그 통제된 궤도 위에서만 언어 모델이 지닌 유연함과 표현력을 마음껏 발휘하도록 돕는 절제의 미학</strong>에 있다.

확률의 바다 위에 기호의 단단한 닻을 내리는 일. 그것이야말로 불확실한 AI 기술을 현실의 산업 현장에 뿌리내리게 만드는 가장 정직하고 우아한 엔지니어링의 길일 것이다.
